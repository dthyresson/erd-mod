# Code Style & Tooling Preferences
- Prefers commands to have aliases for alternate naming conventions (e.g., `/erd-describe` as alias for `/erd-about`). Values discoverability through multiple command names. Confidence: 0.7
- Prefers output/summaries to include database type/dialect metadata (e.g., sqlite, postgres, mysql) for context. Confidence: 0.8
- Prefers markdown tables as the display format for structured schema/column attribute data (columns, types, nullability, keys, defaults, etc.). Explicitly stated as ideal format, reiterated preference for proper markdown support in mod UI. Confidence: 0.95
- Prefers compact individual-line formatting over ANSI box-drawing/grid tables in terminal feed output. Finds box-drawing tables visually poor ("does not look great") and prone to truncation. Confidence: 0.8
- Prefers project-level `.commandcode/settings.json` for per-project configuration (e.g., taste learning). Confidence: 0.8
- Prefers generated output (especially ERDs) to be automatically copied to the clipboard so the user can immediately paste and use the result elsewhere. Values convenience and reducing friction between tools. Confidence: 0.8
- Prefers `.md` file extension for markdown-based generated files (e.g., Mermaid ERDs) rather than format-specific extensions like `.mmd`. Values consistency with conventional markdown file naming. Confidence: 0.8
- Prefers generated artifacts (like ERDs) to be persisted to disk in a dedicated output directory with ISO timestamps for uniqueness, rather than being ephemeral command output only. Values having a retrievable artifact trail. Confidence: 0.8
- Prefers markdown rendering support in command output surfaces (mod feed). Explicitly stated desire for proper markdown support in the mod UI, not just ANSI/terminal formatting; later drove implementation of a markdown→styled-lines feed renderer. Confidence: 0.85
- Prefers generated/derived output files to be excluded from version control via `.gitignore`. Keeps generated artifacts local but out of the repository. Confidence: 0.7
- Prefers comprehensive `.gitignore` files following GitHub community-standard templates (macOS/OSX system files, Node.js artifacts, IDE config, environment files) rather than minimal pattern-only files. Explicitly requested "github standard default for osx etc." Confidence: 0.7
- Prefers CLI flags to accept both `--flag=value` and `--flag value` (space-separated) syntax, not just `=` form. Expects the common convention of space-separated flags to work. Confidence: 0.7
- Prefers a picocolors-style ANSI helper library where colors and styles are set by name (`c.cyan()`, `c.dim()`, `c.bold()`, bright variants, backgrounds) for terminal styling, rather than raw escape codes scattered inline. Explicitly requested this refactor ("an ansi color lib like picocolors to make it easy to set colors by name or style like dim, bold"). Confidence: 0.9
- Prefers rich structured command output via custom feed renderers (`cmd.showEntry` + `cmd.addRenderer` with typed data entries) for diagram/summary/FK-map/index/column views, rather than plain `{message}` strings. Endorsed building custom renderers for each command. Confidence: 0.8
- Prefers markdown-formatted output to be routed through a dedicated custom feed renderer that converts markdown to styled terminal lines (bold headings, bullets, inline code, tables), rather than emitting raw markdown as a plain `{message}` string. Explicitly requested ("implement a custom renderer for markdown and use it for those commands that format markdown"). Confidence: 0.9
- Prefers organizing slash commands as one file per command inside a `commands/` directory with an index registry that wires them up, rather than a single flat commands file. Explicitly requested this refactor ("refactor all cmd.addCommand so commands directory and each its own command file"). Confidence: 0.9
- Prefers declarative color configuration: named constants and a config file that declares the default colors in one place ("consts and a config js file to declare the default colors used so we can change"), rather than hardcoded color literals scattered through renderers. Confidence: 0.9
- Prefers a theme system built on semantic color roles: a `themes/` directory with several named palettes, a registry, and a user setting/flag to pick the active theme or fall back to a default. Renderers should reference roles (accent, table, column, key, fk, muted, etc.) rather than concrete ANSI colors, so the look can be swapped globally. Explicitly requested ("create themes so lets add a theme config file to use to have dir and several themes and then a setting to use a default or pick theme to use"). Confidence: 0.95
- Prefers theme colors to be declared as hex values, backed by a hex→RGB conversion utility in the ANSI color library (e.g., `hexToRgb`) so hex specs resolve to true-color ANSI codes. Explicitly suggested ("may need a hex to rgb converter for ansi color utils"). Confidence: 0.8
- Prefers using reference images (palette screenshots) as the source for theme colors — attaches an image and expects the exact hex values to be extracted and applied to a new theme. Confidence: 0.6
